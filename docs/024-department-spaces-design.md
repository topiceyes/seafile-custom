# 024 - 独立部门共享空间设计

日期：2026-11-04。状态：设计已在本地落地，实施记录和当前边界见 [025](025-department-spaces-implementation.md)。设计基线：产品 1.2.8 / Seafile CE 14.0.9。

## 1. 目标与推荐方案

用户需求：钉钉部门自动获得独立共享空间，成员自动进入所属部门空间，部门主管担任空间管理员；部门共享与手工群组分开。

推荐建立独立的“部门共享”模块：

- 每个业务部门自动创建一个部门空间和一个默认资料库。
- 部门、成员和主管来自钉钉，按稳定 ID 关联。
- 文件业务归属部门，不归某个员工或主管；主管变化不迁移文件。
- 第一版使用 CE 的普通资料库和逐人共享权限，不再创建群组承载新的部门空间。
- Web 有独立导航、页面、成员展示、管理入口和 API。现有手工群组保留原有用途。

层级权限已由用户确认：**普通成员只访问自己的直属部门；上级主管自动管理本部门和所有下级部门。** 多部门任职分别计算，管理权向下继承，普通成员访问权不沿部门树继承。下级主管不因此获得上级或同级空间权限。

## 2. 成熟产品中值得借鉴的部分

| 参考 | 已有产品的做法 | 本项目采纳 |
|---|---|---|
| Google Shared drives | 团队共享空间、文件随空间保留；区分管理与内容操作角色 | 文件归属与员工任职分开；主管是管理角色而不是文件所有者 |
| Synology Drive Team Folder | 共享目录被启用为团队入口，权限跟随底层共享目录 | 独立入口，同时让浏览器与同步客户端使用同一套实际文件授权 |
| Nextcloud Team Folders | 管理员配置共享目录并为团队授权 | 成员由组织信息计算，资料空间长期存在 |
| Seafile Departments | 部门拥有资料库，组织管理与资料库管理结合 | 产品体验借鉴其部门空间；CE 实现使用已具备的普通资料库与用户共享 |

不直接照搬其他产品的多层文件 ACL、禁止下载、只许新增不许删除等细分权限。第一版按当前 CE 能力设计，不在界面承诺无法由服务端和客户端共同执行的权限。

## 3. 为什么现有实现混在群组里

当前 `sync_dingtalk_departments` 用 ccnet group 创建部门，`ExternalDepartment` 记录外部部门 ID 与 group_id 的映射。用户侧 `Groups` 和 `ShareableGroups` 返回这些对象，前端 `LibrariesSubNav.renderSharedGroups()` 又把它们一起渲染到群组区域，只用图标区分部门。

此外，CE 没有 Pro 的组属主库 RPC，因此当前结果主要是“部门对应一个群组，别人把个人资料库共享进来”，没有自动获得组织所有的默认资料库。

只换图标、加一个侧边栏标题不能解决文件归属、主管角色和组织变更的问题。需要独立的业务模型，并让文件核心收到对应的实际授权。

## 4. 产品体验

### 4.1 用户导航

```text
文件
  我的资料库
  与我共享
  部门共享
    研发部                 我是成员
    产品部                 我是主管
  群组
    产品发布项目组
    兴趣交流组
```

部门较多时只列本人可访问的空间，在部门共享首页提供搜索与路径信息。组织树用于定位，不据此扩大文件访问范围；无权限部门不展示文件或资料库名称。

“部门共享”页面是独立的业务页面，空间内文件操作复用现有文件浏览器，避免再做一套上传下载系统。

### 4.2 空间内容

示例：`部门共享 / 研发中心 / 平台部`。

- 文件：自动创建的“平台部共享资料”资料库；名称随部门变更，repo_id 保持稳定。
- 成员：钉钉同步的成员、直属主管、继承管理权的上级主管、待首次登录人员以及同步状态。上级主管标注“来自研发中心主管”等权限来源。
- 管理：主管可见空间管理、恢复等入口；系统管理员有独立的全局管理入口。
- 信息：显示资料归属、所属部门、主管与最近成功同步时间。

首期每部门一个默认库，以目录区分业务资料。数据模型允许以后扩展多个库，但首期不增加建库和库级差异权限的交互。

### 4.3 部门树与目录树

例如“研发中心 / 平台部”和“研发中心 / 应用部”各有独立空间。部门层级不自动变成一个大资料库里的文件夹层级，便于调部门、独立授权和归档。

公司根节点用于组织导航，默认不创建全员可访问的根空间；各实际业务部门自动建空间。空部门也可以建空库，没有直属主管和有效上级主管时由系统管理员托管并显示待配置状态。若钉钉根部门明确配置了主管，该主管按同一继承规则管理整棵部门树；不能把“公司根部门普通成员”误当成全公司管理员。

## 5. 成员和权限规则

### 5.1 权威来源

| 数据 | 来源 | 本系统处理 |
|---|---|---|
| 部门 ID、名称、父级 | 钉钉通讯录 | 同步更新，不能用名称做唯一键 |
| 部门成员 | 钉钉部门成员 | 自动加入和移除；未登录人员先保存关系 |
| 部门主管 | 部门详情的主管列表 | 自动管理该部门及所有下级部门空间，可有多人 |
| 空间文件和历史 | Seafile | 组织人事变化不移动、不删除文件 |
| 空间状态及审计 | 新模块 | 记录开通、降级、同步、归档和管理操作 |

主管应读取 `dept_manager_userid_list`，而不是企业群群主 `org_dept_owner`，也不能通过职位名称猜测。主管列表是 userid，当前 Seafile 钉钉绑定使用 unionid，需要保存并校验 userid → unionid → Seafile 用户的映射。参考 [钉钉部门详情接口官方字段](https://developer.alibaba.com/docs/api.htm?apiId=52330)。接口响应与应用可见范围需要在实施前做只读验证。

不把部门主管设为 `is_staff` 或全站管理员。

### 5.2 首期角色

| 能力 | 本部门成员 | 本部门及上级主管 | 系统管理员 |
|---|---|---|---|
| 浏览、下载、上传、编辑文件 | 可以 | 可以 | 按管理流程授权/接管 |
| 日常移动、重命名和删除文件 | 可以，按 CE 原生 rw 语义 | 可以 | 按管理流程操作 |
| 查看本空间成员 | 可以 | 可以 | 可以 |
| 管理空间设置、管理恢复操作 | 无空间管理权 | 可以，限本人管理分支中的空间 | 可以 |
| 修改钉钉成员和主管 | 不可以 | 不可以 | 应在钉钉处理 |
| 把其他部门人员加入空间 | 首期不开放 | 首期不开放 | 后续通过明确授权功能处理 |
| 转移资料库所有者、删除整个空间 | 不可以 | 不可以 | 独立高风险管理操作 |
| 生成外链、公开共享、跨部门再共享 | 首期默认关闭 | 首期默认关闭 | 按后续策略开放 |

普通成员的 rw 包括删除文件，不能只靠隐藏删除按钮宣称“不能删除”。如果需要只读资料，可后续增加独立只读库；如果需要“可编辑但不可删除”等精细限制，需要另做 CE 核心能力验证。

主管管理权通过空间专用的动作权限实现，不直接给上游通用 `admin` 共享权限。后者会使多个旧接口认为用户可管理库，并可能放开再共享等能力。

对任一部门 D：有效主管 = D 的主管与所有祖先部门主管的并集；有效访问人员 = D 的直属成员与有效主管的并集。每个继承管理授权保留来源部门，避免一条路径撤销时误删另一条仍有效的授权。上级普通成员不会被加入该集合。

已有管理员不再因为 `is_staff` 被永久塞进所有部门成员集合。全局运维管理权与日常部门成员资格分开记录，接管操作留审计。

### 5.3 人事与组织变更

| 变化 | 期望行为 |
|---|---|
| 新部门 | 自动建空间、默认库和部门托管身份 |
| 新成员/首次登录 | 根据有效组织快照补授权，进入后看到自己的部门空间 |
| 调部门 | 撤销旧部门访问，再加入新部门；原文件留在原部门 |
| 多部门任职 | 可进入多个空间，分别计算权限 |
| 主管更换 | 重新计算该部门及全部后代空间的管理与访问权，文件所有者不变 |
| 主管仍是成员 | 撤管理权后仅在本人仍为直属成员的空间保留普通成员读写；不再保留下级访问 |
| 主管不在直属成员列表 | 主管任命本身提供本空间访问，不依赖成员列表偶然包含他 |
| 部门改名 | 修改展示名和默认库名称，不换 ID、不复制文件 |
| 部门换父级 | 更新导航，并重算被移动部门及全部后代的上级主管授权；撤原分支主管、加新分支主管，直属成员访问规则不变 |
| 部门撤销 | 标记待归档；复核后撤日常写权限、保留资料，不自动删除 |
| 员工离职 | 账号禁用与空间授权回收共同处理；员工创建的部门文件保留 |

权限回收针对后续服务端访问；已经下载或同步到个人电脑的副本不会因此自动消失。

## 6. CE 技术方案

### 6.1 方案选择

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 独立空间 + 普通资料库 + 用户共享 | 不再需要部门群组；复用 CE 文件权限与原生客户端 | 需要逐人授权、回收和一致性处理 | 推荐首期采用 |
| 独立空间 + 隐藏技术群组 | 大量成员与多个库时授权关系较少 | 仍需防止技术群组进入各类旧入口，层级权限更复杂 | 保留作后续规模优化选项 |
| 实现新的 C 核心部门所有权与 ACL | 可完全自定义 | 涉及核心、RPC、多端权限和上游升级 | 当前需求无需承担这部分改造 |

按历史文档中的部门和人员规模，首期每部门一个库时，逐人授权值得优先验证。授权条目规模取决于“直属成员与继承主管合并后的有效空间访问关系数 × 每空间库数”，上线前要做批量同步和列表性能测试，包含高层主管管理多个下级空间的情形。

### 6.2 文件归属与主管管理

业务归属由 `DepartmentSpaceLibrary` 绑定到部门空间。CE 底层 owner 使用部门专用的系统托管账号，不使用当前主管、创建者或真实员工账号。

每部门一个托管账号，便于未来隔离用量、配额和生命周期。托管账号不绑定钉钉、不作为人员搜索结果、不提供交互登录或客户端 token，不设全站管理员；系统使用内部服务执行必要的库创建及管理操作。账号的有效状态需要结合文件核心校验验证，不能简单禁用后假设共享仍正常。

不创建 `@seafile_group` 所有者，也不调用 CE 缺失的 `add_group_owned_repo`。新建库使用已有普通建库能力，授权使用当前 `share_dir_to_user()` 最终调用的用户共享能力。

实际上传、编辑和删除仍使用真实操作者身份；托管账号仅承接所有权。管理动作同时记录请求操作者，不能让审计全部变成托管账号。

### 6.3 数据模型建议

新 Django app：`department_spaces`。

| 模型 | 关键内容 |
|---|---|
| Department | provider、稳定组织来源 ID、external_dept_id、parent、name、生命周期状态 |
| DirectoryIdentity | 钉钉 userid、unionid、Seafile 用户名（可空）、最后验证时间 |
| DepartmentMembership | 部门、身份、直属 member/manager 任职来源、快照版本；允许同人同时有成员与主管来源 |
| SpaceRoleGrant | 目标空间、用户、member/manager、来源部门、direct/ancestor_manager、计算版本；区分任职原始数据与继承结果 |
| DepartmentSpace | department 唯一绑定、显示名、托管 owner、provisioning/active/degraded/archived 状态 |
| DepartmentSpaceLibrary | space、repo_id、is_default；一空间至多一个默认库 |
| AccessProjection | repo、用户、目标权限、已应用权限/版本、重试状态 |
| DirectorySyncRun | 范围、完整性、数量变化、开始结束、最后成功版本、错误 |
| SpaceAuditEvent | 操作者、部门/空间/库、动作、前后值、同步批次 |

外部身份比较保留大小写并做精确匹配，不依赖数据库默认排序规则。业务唯一键应包含来源，不能只靠部门名称或跨组织可能重复的 dept_id。

组织树只存于 Department，不再用 `parent_group_id` 表达新的空间层级。`ExternalDepartment` 原映射作为迁移线索保留，不成为新业务的核心主键。

### 6.4 授权执行与一致性

```text
钉钉组织、成员、主管
        ↓ 完整性校验
版本化组织快照
        ↓ 计算有效成员与空间角色
独立部门空间模型
        ↓ 持久化授权计划、幂等执行
CE 用户共享 r/rw
        ↓
网页 / 同步客户端 / SeaDrive / WebDAV
```

不能只在 Django 中记“有权限”。下载、同步和 WebDAV 的文件核心也必须收到实际授权。

Django 事务不能覆盖 C RPC。先保存目标和待执行任务，再幂等调用 RPC，成功后更新投影版本；中途失败可重试和对账。撤销旧访问先于新增访问，失败时不把空间标为全部同步成功。主管角色撤销在新模块权限检查中即时生效，文件共享按投影执行状态跟踪。

同一用户有多个有效角色来源时，只有最后一个访问来源消失才撤回核心共享。首期不开放任意手工成员，避免同步把人工授权误删。

开通库也需要幂等：先创建唯一空间任务，再创建库；RPC 成功但数据库回写失败的窗口要有可追踪的开通标记和对账，不能仅靠库名称判断归属或重试后重复建库。

### 6.5 同步策略

- 首期沿用每小时全量对账，并在登录后对该用户做补偿授权；变更在下一轮成功同步后生效。若要求分钟级回收，再接钉钉事件和更短周期，不能把轮询描述为即时同步。
- 首次登录既读取已验证的快照，也要处理身份映射缺失；补偿失败需显示开通状态并重试，不能默默等一小时。
- 拉取完整组织及成员/主管数据、校验分页、可见范围和组织树无环后，才能提交需要撤权的批次。父级断链或树异常时不推导继承管理权。
- 失败、字段缺失、分页中断不能解释为“成员为空”或“没有主管”。只有完整且可信的空列表才代表清空。
- 数量突降、批量移除超阈值、数据长时间未刷新时报警并暂停本轮批量变更。离职账号禁用仍作为独立防线。
- 显式请求超时、退避重试、单任务互斥、非零失败状态、最近成功时间与批次统计。
- 第一版由新命令接管组织同步；旧命令不能继续对新旧群组与空间同时写入。

## 7. API 与旧功能隔离

建议新增接口族：

```text
GET  /api/v2.1/department-spaces/
GET  /api/v2.1/department-spaces/{space_id}/
GET  /api/v2.1/department-spaces/{space_id}/members/
GET  /api/v2.1/department-spaces/{space_id}/libraries/
GET/PATCH /api/v2.1/department-spaces/{space_id}/settings/
GET  /api/v2.1/admin/department-spaces/
POST /api/v2.1/admin/department-spaces/reconcile/
```

文件浏览上传下载复用原 repo_id 接口。业务权限通过统一的 `can_manage_space`、`can_access_space` 等策略执行，不能分散写成“是主管就放行”。所有管理接口检查对象所属空间，防止传入其他部门 repo_id 越权。

以下旧入口也要处理：

- 手工群组列表、共享目标、成员管理等不再返回已迁移的部门映射对象；新空间没有群组对象可混入。
- 部门默认库在 Web“部门共享”集中展示，在通用“与我共享”页面去重。不能全局从 `/api2/repos/` 删除这些库，否则原生客户端可能失去发现入口。
- 在兼容库列表中保留原字段和共享类型，可补充 `business_type=department_space`、space_id、部门显示信息；旧客户端忽略新字段仍能读写。
- 禁外链、禁跨部门再共享等规则必须覆盖新旧分享 API、上传链接、公开链接及相关 token 入口，不只是隐藏新页面按钮。
- 托管账号从用户搜索、分享候选人等入口排除，但保留给运维检查的明确管理视图。

未修改的原生客户端第一版可把这些库显示为“共享资料库/与我共享”，名称显示部门来源。自定义“部门共享”分类首先在 Web 实现；客户端也要专用导航，需要分别改客户端，不能靠后端保证原版客户端新增菜单。

## 8. 旧部门群组与资料迁移

1. **只读盘点。** 按 ExternalDepartment 的 provider 和外部 ID 标记自动部门，列出关联群组、成员、共享库及 owner；不能按名称批量删除，以免伤到手工群组。
2. **开通新空间。** 用稳定部门 ID 创建独立模型、托管身份和默认库。先选测试部门验证，不立即撤旧访问。
3. **分类现有资料。** 新的默认库是部门资产；原来共享给部门的个人库仍归原 owner，不能自动据此判定为部门资产。
4. **处理历史共享。** 先在迁移台账中明确哪些保持个人归属、哪些经负责人确认后转为部门资产。保持个人归属的库可以作为独立的历史共享引用展示；保留 owner、共享来源和原权限，不宣称它是托管部门库，也不自动扩大成员范围。
5. **验证新授权后切换入口。** 原群组授权向逐人授权转换时保存原有效用户集合和权限，逐项比对；转换成功后才撤对应旧授权。资产转移要验证 repo_id、历史、链接和客户端同步连续性，不能假设换 owner 没有其他副作用。
6. **退役旧部门群组。** 先停旧同步、隐藏旧入口，确认无库、权限与客户端依赖，再移除旧群组。手工群组完全由原功能继续管理。

迁移前需要可恢复备份和权限快照。回退必须恢复数据映射、分享关系和功能开关，不能只切回旧镜像后就认为新权限自动消失。迁移中断时保留台账，重跑不重复创建空间或丢失旧访问。

## 9. 实施顺序与验收

### 阶段 A：证明核心路径

使用一个父部门、两个子部门和一个无关部门，以及成员和主管，验证：CE 普通托管库、逐人共享、多端读写、撤权、主管继承与越权拒绝、禁止再共享。核对主管接口字段和 userid/unionid 映射。此阶段是后续开发的技术门槛。

### 阶段 B：实现独立业务闭环

新模型与同步、自动建空间/默认库、独立导航和页面、主管管理、服务端策略、授权投影对账；停止创建新的部门群组。首期完成需求核心，不加入文件夹细粒度 ACL 和跨部门临时协作。

### 阶段 C：灰度迁移和发布

先选一个现有部门迁移历史共享与入口，检查真实客户端后扩大。全量迁移通过才退役旧部门群组。

关键验收场景：

- 新建部门后出现独立空间与默认库，手工群组列表和分享候选群组没有新增部门。
- 未登录成员先有组织关系，首次登录后能进入正确空间，不需要手工邀请。
- 同名部门、多部门任职、多人主管、主管非直属成员均正确匹配。
- 上级主管能管理整个下级分支；上级普通成员看不到下级资料；子部门主管看不到同级和上级资料。
- 主管不是全站管理员；伪造其管理分支之外的 space_id/repo_id 返回拒绝。
- 人员调动、主管更换、撤销角色后，新旧网页/API/客户端的权限与目标一致。
- 修改部门名称和父级不重复建库、不移动文件；跨分支移动后旧上级主管失权，新上级主管获得管理权，普通成员范围不随树形变化扩大。
- 成员日常 rw 可以删除文件；删除后的恢复按设计工作；删除整个空间、转移 owner、生成公开链接不能绕过策略。
- 同步分页失败、通讯录权限缩小、主管字段缺失、RPC 中断、并发重试，不发生误清空或重复开通。
- 历史个人库没有被自动转移所有权，旧分享向新授权迁移后没有多给或少给人员。
- 普通手工群组原有创建、成员、分享和文件访问不受部门新模块影响。
- 备份恢复包括新模型、权限快照与 C 核心分享关系；恢复后可访问历史文件。
