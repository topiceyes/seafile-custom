复盘日期：2026-11-04。检查对象：主仓库 `1efeb9a`、本地 seahub `532a2a7a`。

本次依据 Git 历史、现有知识库、补丁和部署代码进行复盘，并做了离线补丁重放、语法检查和隔离逻辑探针。未连接生产服务器、未核验当前线上镜像与备份、未重新执行完整 Docker 彩排。文档里的灰度结果属于历史记录，不能等同于本次实测。

## 1. 总体判断

项目已经完成从“钉钉扫码登录改造”到“企业网盘账号、组织和发布体系”的演进。当前产品版本是 **1.2.8**，上游是 **Seafile CE 14.0.9**。

最有价值的成果是：把企业身份和组织关系接入现成文件平台，同时建立了补丁复现、镜像构建、发布追溯和反代彩排机制。主要短板是：交付证据偏向源码、镜像和配置一致性，持续运行与用户业务验收的覆盖不足。接下来应优先做稳定性收尾。

用户说明本项目由 CC 辅助二开。仓库能支持对产物和工作方法的评价，但没有完整会话、耗时、成本和人工介入记录，不能据此计算 CC 的效率提升或把每个缺陷归因于 CC。

## 4. 做得好的技术取舍

1. **二开集中在 Web 与部署层。** 复用现成文件核心，定制主要围绕企业身份、管理和交付，控制了维护面。
2. **补丁有固定基线和目标树。** 本次在临时仓库重放全部 10 个补丁，得到 `9b584dcb6acfb8f7ad2295cf9d8c7ff88fb83741`，与 MANIFEST 和本地 seahub HEAD 的 tree 完全一致。这条证据真实有效。
3. **构建与验证入口集中。** 本地和 CI 共用构建脚本、冒烟脚本；发布先验镜像再移动通道，并检查 digest，减少多套实现互相漂移。
4. **减少部署时的隐含手工步骤。** 把定制 bootstrap、脚本与 cron 烘进镜像；配置按启动时机处理，考虑了幂等和已有数据卷。
5. **有较完整的故障记录。** 文档记录了根因、修复和灰度证据，也有主动撤回未完成验证声明的记录，有助于后续维护。

上述机制值得保留。但树哈希只证明“补丁复现了记录的代码”，不会判断记录的代码是否漏掉需求。文档 016 的解绑禁令遗漏正好说明这个边界。

## 5. 本次确认的遗留问题

### 优先级 1：备份默认链路没有闭合

`deploy/image/backup.sh:18` 强制要求 `DB_ROOT_PASSWD`，主机名读取旧变量 `DB_HOST`。生产 compose 目前传入的是 `INIT_SEAFILE_MYSQL_ROOT_PASSWORD` 与 `SEAFILE_MYSQL_DB_HOST`，没有把旧变量传给备份脚本。

备份 cron 又直接调用该脚本，没有加载环境的步骤。019 已明确记录 cron 拿不到主进程容器环境；该次修复为 seahub.sh 生成了 conf/.env，但没有覆盖直接运行的备份脚本。

本次用清空环境的隔离执行验证：脚本在任何备份写入之前以退出码 1 中止，报缺少 `DB_ROOT_PASSWD`。这证明仓库默认链路存在问题；线上是否有额外配置或人工备份，本次未核验。

建议先核实最近一次成功备份和恢复，再统一备份取配置的方式，验证真实 cron 环境下能导出三库与文件数据。备份成功应有明确完成标记、失败状态与可检查的最近成功时间。异地副本在现有文档中仍是后续项。

### 优先级 1：同步失败的退出状态与安全边界不足

离职同步在 token 获取失败、成员拉取失败或成员集为空时，记录错误后直接 `return`。部门同步也有类似路径。对 Django 管理命令而言，这些返回路径没有声明失败，cron 的 `|| echo FAILED` 无法覆盖它们。

本次提取离职命令类并注入失败 token：得到错误信息，但 `handle()` 正常返回，验证了这一控制流。同步 API 请求还没有显式 timeout；遇到长时间无响应时可能拖住任务。

现有离职同步会在完整拉取成功后才执行禁用，并有空集合保护，这是有效防线。但“非空集合”不能证明通讯录可见范围完整：如果授权范围收窄而接口仍返回部分人员，就有把范围外账号判断为离职的风险。此处是风险分析，没有证据证明线上发生过误禁用。

建议异常使用明确失败状态；区分正常跳过与失败；加入请求超时、任务互斥、最近成功时间，以及通讯录数量突降/批量禁用阈值。部门同步成员移除也应纳入类似保护。

### 优先级 2：部门换父级不会跟随同步

`sync_dingtalk_departments.py` 的 `_sync_tree()` 对已有映射只处理部门不存在和名称变化，随后跳过，不比较或更新父部门。

隔离逻辑探针中，已有子部门父级为 100，钉钉输入要求父级为 200；同步后仍为 100。创建时层级正确，后续组织调动会发生漂移。父部门创建失败时，当前逻辑还可能把子部门建到顶层，后续同样缺少纠正。

建议把父级变更作为独立同步动作，并定义父级创建失败的处理方式。

### 优先级 2：设备可见性兜底无法唯一识别物理设备

`seahub/views/sso.py:67` 用 `sha1(用户名|浏览器 UA)` 生成兜底 device_id。同一用户在不同电脑使用相同 UA，会生成相同 ID；TokenV2 管理器对相同用户、平台与 ID 复用同一 token。

因此该方案能补充设备记录，但不能保证“一台物理电脑一条记录”。管理员解绑或擦除一条记录可能影响共享该 token 的多台客户端；浏览器 UA 更新也可能产生额外记录。这个结论针对缺少真实设备参数的兜底路径。

建议优先修复或升级客户端的真实设备参数传递。在兼容方案仍需保留时，界面与运维说明应明确识别精度。

### 优先级 2：只改冒烟脚本，CI 可能跳过新断言

workflow 的 paths 包含 `deploy/smoke-test.sh`，但发布守卫只比较镜像、通道 digest 和 Release 资产。当它们都未变时，push 路径设置 `mode=none`（第 278 行），后续冒烟步骤又排除该模式。

所以“只改 smoke-test.sh → 自动触发 → 已发布完整 → mode=none → 跳过冒烟”这条路径仍然存在，与注释声称的重验效果不一致。本项由控制流审查确认，本次未远程运行 Actions。

建议让验证脚本变更可以单独重验现有镜像；镜像无需重建与验证无需执行应分别判断。

### 优先级 2：入口文档与验收状态需要收口

根 README 前部仍把项目写作基于 12.0，并给出 `0877ad7` 的应用命令；末尾已改为 14.0。`docs/README.md` 的关键约定仍写 12.0.14、Django 4.2，和当前版本冲突。009 的证书恢复说明还沿用容器内 LE 模式。

014–017、021、022 等文档中仍存在浏览器、扫码或客户端待验项。部分标题写“全绿”，正文却保留用户侧未验，应将服务端验证与业务验收分别标注。

建议当前状态集中维护一份，历史文档保留当时事实；修正入口命令，并完成一轮真实用户验收。

## 6. 对 CC 辅助二开方式的复盘

从产物看，CC 辅助工作的优势体现在跨层落地：能同时处理 Django、React、容器启动、nginx、CI 和操作文档，并把现场故障转化为脚本和断言。

需要加强的是验收约束。历史上多次用“配置存在、补丁标记在位、镜像一致”支持功能完成，但这些证据分别只回答了局部问题：

| 验证证据 | 能证明什么 | 还需要验证什么 |
|---|---|---|
| tree SHA 一致 | 补丁复现当前源码 | 需求是否完整迁移、行为是否正确 |
| cron 文件与路径正确 | 定时命令已配置 | cron 环境下能执行、能持续成功 |
| 部门 API 可创建 | 部门入口可用 | 通用列表、共享权限、调部门后的行为 |
| 登录页 200、接口成功 | 服务或接口可访问 | 真扫码、客户端链接、用户实际操作 |
| 能切回旧镜像 | 镜像版本可选择 | 数据库变更后的实际恢复能力 |

后续交给 CC 的任务，应包含业务不变量、负向场景、已有数据迁移和验收证据。例如“禁止解绑”需要验证直接请求后绑定仍在；“离职禁用”需要验证通讯录异常时不会批量误禁用；“组织同步”需要覆盖换父级。

## 7. 建议的下一轮工作

1. **先恢复运维可信度。** 核实并修复备份的真实 cron 执行，完成一次包含历史文件的恢复；补齐同步失败状态与最近成功时间。
2. **补业务边界。** 部门换父级、通讯录范围异常保护、设备兜底识别精度、成员与非成员共享权限。
3. **补升级与发布验证。** 建立旧卷升级场景；按需求逐项核对补丁行为；保证只改验证脚本也能重验镜像。
4. **完成验收与文档收口。** 真实用户完成两域名扫码、客户端链接与设备管理、部门共享与检索；统一 README、版本边界和验收状态。

适合固定为发布回归的业务链路：登录与禁密码、禁解绑、客户端链接、文件上传下载、部门共享权限、人员/部门变动、cron 实际执行、旧卷升级、备份恢复。重点是覆盖历史故障所代表的行为，而非继续增加文件存在性检查。
